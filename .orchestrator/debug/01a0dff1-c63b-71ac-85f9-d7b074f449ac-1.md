### Hypothesized root cause

The shared test database factory reconnects to Docker Postgres through Windows `localhost` without a timeout, so the IPv6-first connection path waits indefinitely even though the IPv4 service is healthy. · Confidence: high

## Phase 2 — Pattern

This is the same host-resolution class recorded in TASK-50 notes: `localhost` resolves to `::1` first on Windows while the compose service is reachable immediately on `127.0.0.1`. The fixture guards only its initial probe with `connect_timeout=3`; database creation and cleanup repeat the vulnerable unbounded connection pattern. The runtime defaults share the same hostname, so DBOS/application startup can suffer the same delay.

A regression check should assert the committed local-compose URLs use `127.0.0.1` and every direct test-fixture `psycopg.connect` has a finite timeout.

## Phase 3 — Impact

Affected paths:

- `.env.example` — local compose URL copied by users.
- `src/relay/config.py` — runtime default database URL.
- `tests/conftest.py` — initial probe, database creation and cleanup connections.
- Every database-backed client, delegator, executor and store test depends transitively on `migrated_db_url`.

Changing only one test would leave all sibling database tests and runtime startup exposed. The fix belongs in the shared URL defaults and shared fixture connection boundary.

## Phase 4 — Solution

Use `127.0.0.1` for the local Docker Postgres defaults and add `connect_timeout=3` to every direct fixture connection. Add one small regression assertion for the default URL/timeout behavior if existing settings tests do not cover it. Then rerun the isolated failing test and the full quality triad.

## Resolution

Fixed shared defaults/examples to `127.0.0.1` and added `connect_timeout=3` to database creation and cleanup. The isolated database-backed client test passed in 0.69 s; final full suite: 524 passed, 25 skipped.
